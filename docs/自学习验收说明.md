# 自学习验收：双闸、退步闸门与回滚

> 一句话：自学习是「让系统自己改自己的知识」。没有验收，就等于给车装了油门却没装刹车——某次学进一条错话术，线上会一直错下去，而且没人知道是哪天变坏的。
> 这套机制就是那脚刹车：**学的东西先进待验证区，跑分通过了、店长确认了才生效；一旦变差，自动拒绝并支持整批回滚。**

---

## 一、为什么必须有这层东西

在验收机制之前，教学接口 `POST /api/teach` 是**直写直生效**的：店长（或后续的自学习脚本）写进去一条样本，下一句对话就可能被召回、被模型模仿。

问题在于：这条样本**可能是错的**。典型错法有三类——

| 错法 | 例子 | 后果 |
|---|---|---|
| 政策说错 | 「拆封用过也能退」 | 客户拿着这句话来退货，公司兜底 |
| 乱承诺 | 「给您降 200」 | 价格体系被一句话击穿 |
| 该升级的不升级 | 「不用找领导，给您补个红包」 | 投诉被压下，客户转头去 12315 |

人教的还能靠人把关，**模型/脚本自己归纳出来的样本没人看过**——出错的概率更高。所以验收不是可选项。

## 二、五道关

### 第 1 关：固定评估集（20 题，可复现）

`data/eval_set.json` 里固定 20 道题，覆盖六类能力：

| 类别 | 题数 | 考什么 |
|---|---|---|
| 商品咨询 | 4 | 能否答出真实价格/型号，不编造 |
| 比价砍价 | 3 | 守住价格，用券/活动替代直降 |
| 物流 | 2 | 发货时效、到达时间 |
| 售后 | 4 | 退换政策边界、隐私边界 |
| 必须转人工 | 4 | 假货索赔、投诉、12315、明确要人工 |
| 超范围 | 3 | 要老板电话、问宠物用药、让写代码 |

每题的判分项：

```json
{
  "id": "E05",
  "expect_handoff": false,          // 该不该转人工：true/false/any
  "must_any": ["券", "优惠", "活动"], // 应答要点，命中任一即可
  "forbid": ["降200", "减200"],      // 事实红线，出现即扣分
  "max_chars": 180                  // 简洁度上限
}
```

**同一套题反复跑，分数才可比。** 换题就等于换考卷，前后对比无意义。

### 第 2 关：影子跑分（不改线上）

候选样本进来时是 `status='pending'`，召回 SQL 只认 `status='active'`，所以它**不会**被真实客户碰到。

但验收又必须知道"它生效后会怎样"，于是跑分时对**当前进程**临时放行这个批次：

```python
playbook_service.shadow_allow(batch_id)   # 只在本进程内让这批参与召回
try:
    ...跑 20 题...
finally:
    playbook_service.shadow_clear()       # 无论如何撤销，库里状态不变
```

这就是影子流量（shadow traffic）的思路：**用真实的召回链路测，但不真的推给客户**。

### 第 3 关：退步闸门

跑完与上一轮台账对比：

```
综合分 = 0.35×转人工判断 + 0.30×应答要点 + 0.20×事实红线 + 0.15×简洁度
```

- 跌幅 ≤ `EVAL_REGRESS_TOLERANCE`（默认 0.05）→ `pass`，可生效
- 跌幅 > 阈值 → `regress`，**这批样本不予转正**，退出码 2（可直接卡 CI）

权重这样定的理由：转人工判断错最贵——该转不转会把投诉逼成舆情，不该转乱转会白烧人力；其次是答不到点上；再次是说错事实；最后是啰嗦。

### 第 4 关：双闸确认（人签字）

跑分通过只是第一道闸，第二道闸是**店长点确认**：

```
pending ──跑分通过──> 店长确认 ──> active（参与召回）
   │                      ↑
   └──跑分退步──> 拒绝 ───┘
```

- 逐条确认：`POST /api/learn/sample/{id}/activate`
- 整批确认：`POST /api/learn/batch/{batch_id}/activate`
- 待验证列表：`GET /api/learn/pending`

为什么还要人？因为 20 题只能测"有没有变差"，测不出"这条话术是否符合品牌调性"。机器管退步，人管取舍。

### 第 5 关：一键回滚 + 台账

**回滚**按批次整体撤销，不物理删除（`status='rolled_back'`）：

```bash
python scripts/eval.py --rollback b20261127
```

置位后立刻从召回中消失，但数据留着，方便复盘"这批到底学了什么、为什么回滚"。

**台账**（`eval_runs` 表）每次跑分留一行：批次号、题数、通过数、综合分、各项分指标、结论、与上轮的差值、时间。

```bash
python scripts/eval.py --history
```

| run | 时间 | 分数 | 通过 | 结论 | 批次 |
|---|---|---|---|---|---|
| 3 | 2026-11-27 13:4x | 1.000 | 20/20 | pass | - |
| 2 | 2026-11-27 13:33 | 0.982 | 19/20 | pass | - |

出问题时，这就是"什么时候、因为哪批学习、掉了多少分"的证据链。

## 三、怎么用

```bash
# 1. 自学习产出一批候选（写进待验证区，不生效）
python scripts/learn_batch.py --batch b20261127 --file data/learn_candidates.json

# 2. 影子跑分（这批临时参与召回，测它生效后的效果）
python scripts/eval.py --batch b20261127

# 3a. 通过 → 整批转正
python scripts/eval.py --batch b20261127 --activate

# 3b. 退步 → 保持待验证，或直接回滚
python scripts/eval.py --rollback b20261127

# 平时体检（不带批次，只看当前线上状态）
python scripts/eval.py
```

后台也能点：`POST /api/eval/run`、`GET /api/eval/history`、`GET /api/learn/pending`。

## 四、实测记录(2026-11-27,真实模型 qwen-flash)

### 4.1 基线

15 条已生效样本,20 题,耗时 52 秒:

| 指标 | 数值 |
|---|---|
| 综合分 | **1.000** |
| 全项通过 | 20/20 |
| 转人工判断 | 100% |
| 应答要点 | 100% |
| 事实红线 | 100% |
| 简洁度 | 100% |

### 4.2 注入错误样本:两次都没被击穿

**第一次**:3 条错误样本(降价承诺 / 拆封可退 / 红包压投诉),逐条与正确答案争夺召回位置。

结果:综合分 **1.000**,20/20。三条错误示范都进了 top-2 召回,但模型在"正反两条并存"时选了正确的那条。

**第二次**:6 条错误样本,同主题多条集中投放,意图挤掉正确样本;同时**影子重算总纲**(错误样本会污染全局策略,这才是最危险的地方)。

结果:综合分 **1.000**,20/20。E18/E19 反而开始转人工了——说明总纲确实被改写了,但错误话术仍被挡住。

**为什么没掉分?** 因为这个系统有四层防御,闸门只是最后一层:

| 层次 | 机制 | 挡住的错误 |
|---|---|---|
| 1 | 业务设定铁律(店长写的全局约束,注入系统提示最前) | 大方向跑偏 |
| 2 | 套路总纲(归纳层,冲突时以总纲为准) | 具体策略跑偏 |
| 3 | 关键词强制转人工(`_wants_human`,规则层,不过模型) | 投诉/12315/明确要人工被压下来 |
| 4 | 模型自身对齐 | 明显不合理的承诺 |

**这个结果比"掉分"更有价值**:说明"学坏一条就崩"的脆弱性不存在。但也要说清——**这是单次、小批量的注入**。真实风险是长期漂移:几十批样本累积,总纲被一点点改写,单次跑分永远看不出异常。那才是台账存在的意义。

### 4.3 闸门本身可信吗?

"没掉分"不能证明闸门有效——也可能是闸门自己坏了,永远是 1.000。所以另写了一套**确定性自检**,不调模型:

```bash
$ python scripts/test_gate.py

[1] 判分规则:坏答案必须被判低分
  ✓ E05 答应降价 → 失分  (score=0.5 违规=['降200'])
  ✓ E15 投诉未转人工 → 失分  (score=0.45)
  ✓ E10 回复超长 → 简洁度扣分  (210 字 > 180)

[2] 退步判定:跌幅超过阈值必须拦
  ✓ 跌 0.10(>0.05)→ regress  (delta=-0.1)
  ✓ 跌 0.01(≤0.05)→ pass

[3] 回滚:置位后必须立刻从召回中消失
  ✓ pending 不参与召回(第一道闸)
  ✓ 影子放行后可召回(验收行为)
  ✓ 确认生效后可召回(第二道闸)
  ✓ 回滚后立即召回不到  (rolled_back=1)

全部通过:判分、判定、回滚三处均按预期工作
```

判分能识别坏答案、跌幅超阈值必拦、回滚立即生效——三件事都是确定性的,不依赖运气。

### 4.4 台账实录

```
run  时间                  分数    通过    结论      批次
7    2026-11-27 13:41:15  1.000  20/20   pass     b20261127-bad2
6    2026-11-27 13:39:10  1.000  20/20   pass     b20261127-bad2
5    2026-11-27 13:37:35  1.000  20/20   pass     b20261127-demo
4    2026-11-27 13:36:32  1.000  20/20   pass     -
3    2026-11-27 13:35:21  0.985  19/20   pass     -
2    2026-11-27 13:33:44  0.982  19/20   pass     -
1    2026-11-27 13:32:47  1.000   2/2    baseline  -
```

run 2→3 的那 0.015 不是系统退化,是**评估集校准**:E01 原本问"扫地机器人多少钱",模型按套路先反问面积,被判"没报价"。改问"X1 Pro 现在多少钱"(指名型号)后,考核意图才干净。**评估集本身也要被审视**,否则会在考"套路"还是考"直答"之间来回摇摆。

### 4.5 回滚实测

两个演示批次各 3 条 / 6 条,执行回滚后:

```
批次一览:
  b20261127-demo  rolled_back  3 条
  b20261127-bad2  rolled_back  6 条
样本状态:active 15 / rolled_back 9
```

置位后立即从召回消失,线上回到 15 条。数据不删,复盘时能查"这批到底教了什么"。

## 五、局限(写在明处)

1. **20 题样本小**:能测出"明显变坏",测不出"细微退化"。题量应随业务扩张逐步加到 50~100。
2. **判分靠关键词**:`must_any` 命中即算过,措辞不同可能误判。彻底解法是引入人工标注集做校准,或加一层 LLM 裁判(但要单独验证裁判本身的一致性)。
3. **影子放行是进程内的**:多 worker 部署时,只有跑分的那个进程看得到候选样本。生产环境应改为在召回 SQL 上带 `shadow_batch` 参数,按请求透传。
4. **退步阈值 0.05 是经验值**:题量变大后应按统计显著性调整,而不是固定百分比。
5. **回滚不删数据**:`rolled_back` 的样本仍占库,长期需定期清理,避免表膨胀。
6. **闸门难被击穿 ≠ 不需要**:实测两次注入都没掉分,说明系统有多层防御;但单次跑分对"长期累积漂移"不敏感——这正是台账(逐次对比)存在的理由,而不是"跑一次满分就万事大吉"。
7. **评估集本身会偏**:E01 的返工说明题目措辞会决定考什么。每次改题都必须重跑基线,并把改动记进台账 note。

## 六、代码位置

| 文件 | 作用 |
|---|---|
| `data/eval_set.json` | 20 题评估集与判分规则 |
| `app/services/eval_service.py` | 跑分、判分、退步判定、台账读写、影子放行 |

| `app/main.py` | `/api/learn/*`、`/api/eval/*` 路由 |
